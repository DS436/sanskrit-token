# Decision log

Append-only. Newest entries at the bottom. Format per CLAUDE.md §11.

## 2026-09-03 — Use SLP1 as internal encoding
Why: CharSS 2024 and ByT5-Sanskrit both report SLP1 outperforms Devanagari for neural models; it is lossless and ASCII.
Alternatives: IAST (diacritics complicate tokenizer training), Devanagari (byte-level fragmentation).
Reversible: yes, at cost of re-running tokenizer training.

## 2026-09-03 — SLP1 roundtrip is guaranteed for Devanagari/IAST only, not for embedded Latin text; no NFC normalisation
Why: SLP1 is itself an ASCII scheme, so `from_slp1` must read Latin letters as phonemes, ASCII digits as Devanagari digits, and `'` `.` `~` `|` as avagraha, danda, candrabindu and Vedic ḻh. A line mixing English with Devanagari therefore cannot roundtrip — `from_slp1` has no way to tell "The" from a run of SLP1 phonemes — and fixture line 10 of `tests/fixtures/devanagari_sample.txt` is kept as a strict `xfail` documenting that boundary. Unicode NFC normalisation was *not* added to `to_slp1`: the eleven pure-Devanagari fixture lines roundtrip without it, and normalising inside `to_slp1` would in fact break identity roundtrip for any decomposed input (the output would come back composed). Callers that need decomposed text handled must normalise on ingest, in `data/`.
Alternatives: wrapping Latin runs in `sanscript` toggle markers (`##`) so they survive the reverse trip — rejected, it injects non-Sanskrit markers into the SLP1 string that tokenizers are trained on, which is the whole point of the encoding. Per CLAUDE.md §2.3 the original script is stored alongside the SLP1 form instead.
Reversible: yes; adding NFC or a toggle-based passthrough is a local change to `encoding.py` plus its tests.

Why: `load_flores` tries four sources in order and the first three all failed on this machine, so the download that produced `data/raw/flores/devtest.jsonl` (1012 devtest sentences, `san_Deva`/`hin_Deva`/`eng_Latn`) came from source 4, `https://dl.fbaipublicfiles.com/nllb/flores200_dataset.tar.gz` (sha256 `b8b0b767...944011f6`). Failures, in order: (1) `openlanguagedata/flores_plus` — `DatasetNotFoundError: Dataset 'openlanguagedata/flores_plus' is a gated dataset on the Hub. You must be authenticated to access it.` (no `HF_TOKEN` here); (2) `facebook/flores` — same `DatasetNotFoundError`, now also gated, and independently unusable because `datasets` 5.0.1 has dropped `trust_remote_code` and loading scripts ("trust_remote_code is not supported anymore"); (3) `Muennighoff/flores200` — `RuntimeError: Dataset scripts are no longer supported, but found flores200.py`, the same `datasets` 5.x restriction. The tarball is the upstream release the Hub copies are all derived from, needs no Hub account, and is read with `urllib.request` + `tarfile` from the standard library, so it adds no dependency. It is extracted through `tarfile.extractfile` for only the requested `<split>/<lang>.<split>` members, so no archive path is ever written to disk.
Alternatives: obtaining an `HF_TOKEN` and accepting the `flores_plus` licence (better long-term — `flores_plus` is the maintained release with per-sentence metadata — but it needs a credential this machine does not have, and gating makes the pipeline non-reproducible for anyone without one); pinning `datasets<4` so loading scripts still run (rejected, it would drag the whole environment backwards for one corpus).
Reversible: yes. The four sources are tried in order on every call, so simply setting `HF_TOKEN` and re-running `load_flores` switches the download to `flores_plus` with no code change; the sentences are the same FLORES-200 devtest either way, and only `data/README.md` would need its provenance row updated.

## 2026-09-03 — Report `len(tokenizer)` as an arm's `vocab_size`, not `tokenizer.vocab_size`
Why: the two disagree wherever a repo adds special tokens on top of the base vocabulary — Llama-4 Scout reports `vocab_size` 200000 while its ids run to 201134, Gemma-3 reports 262144 against 262145. The id space is what an embedding matrix must cover and what makes vocabulary sizes comparable across arms, so it is the number carried into `results.json`. For `T0_o200k` the equivalent is tiktoken's `Encoding.n_vocab` (200019).
Alternatives: `tokenizer.vocab_size` (understates every repo with added tokens); reporting both (extra field with no consumer yet — add it if a later experiment needs the split).
Reversible: yes, one line in `_hf_vocab_size`; no stored artefact depends on it until Experiment 01 writes its `results.json`.

## 2026-09-03 — Experiment 01 summarises metric distributions as mean + population std, and drops the per-item lists from `results.json`
Why: `fertility`, `compression` and `parity` each return a per-item distribution (`per_word`, `per_text`, `per_pair`) alongside `value`. Written verbatim, three arms × three languages × two script variants × 1012 sentences (and ~25k words per language) would put on the order of a million floats into `results.json`, making it unreadable and unusable in diffs. Each result is therefore reduced by `summarise_metric` to `{value, n, unit, distribution, mean, std}`, where `distribution` names the key that was summarised, `mean` is `statistics.fmean` over it and `std` is `statistics.pstdev` (population std, matching `numpy.std`'s default; `0.0` for a single item). `mean` is kept even though it duplicates `value` for fertility, because for compression and parity the metrics pool numerator and denominator over the whole corpus, so the mean of the per-item ratios is a genuinely different number and is the one that pairs with `std`.
Alternatives: writing the full distributions (unreadable, and git-hostile); writing them to a separate `distributions.npz` per experiment (deferred — no consumer needs them yet; add it when a figure needs a histogram); reporting sample std with `ddof=1` (rejected for consistency with `numpy.std`, which later experiments will use).
Reversible: yes. `summarise_metric` is one function in `experiments/01_baseline_penalty/run.py`; re-running the experiment regenerates `results.json` in ~13 s.

## 2026-09-03 — Report SLP1 roundtrip failures in three buckets, not two, and never abort on them
Why: the plan asked for a roundtrip assertion over every `san_Deva` sentence, split into failures that contain Latin letters (expected: SLP1 is ASCII, so `from_slp1` cannot tell an English word from a run of phonemes) and "pure Devanagari" failures that would indicate a real transliteration gap. On FLORES devtest that cut is not tight enough: 317/1012 sentences fail, 92 with Latin letters and 225 without — but 136 of those 225 merely contain ASCII digits ("4", "2016"), which `from_slp1` renders as Devanagari digits, and of the 89 that contain no ASCII letter or digit at all, nearly all are ASCII `.` or `|` used as danda (SLP1 reads `.` as danda and `|` as Vedic ḻh), with a single genuine nukta case at index 28 (`प़ृ` → `ऋ`). Reporting only "225 pure-Devanagari failures" would have badly overstated the problem. `roundtrip_report` therefore keeps `failures_with_latin` and `failures_pure_devanagari` (the latter meaning "no Latin *letter*", as specified) and adds `failures_no_ascii_alnum` plus `examples_no_ascii_alnum`, which is the bucket actually worth reading; the WARNING log prints all three. The run does not abort, because every metric is computed on the original script *and* on SLP1 and both are reported, and the corpus keeps the original script alongside (CLAUDE.md §2.3), so nothing downstream depends on the reverse direction being lossless.
Alternatives: asserting and aborting (would make Experiment 01 unrunnable on the real corpus for a reason that does not affect any of its numbers); normalising ASCII digits and `|` to their Devanagari equivalents on ingest (rejected here — it would silently edit the corpus every later experiment is measured on; if it is ever wanted it belongs in `data/`, with its own decision entry).
Reversible: yes; the buckets are computed in one function and no stored artefact other than `results.json` depends on them.

## 2026-09-03 — Experiment 01 config paths resolve against the repository root, not the working directory
Why: `config.yaml` holds `flores_jsonl: data/raw/flores/devtest.jsonl` and `output_dir: outputs/01_baseline_penalty`. ## 2026-09-03 — Report the Hindi SLP1 variant as approximate, and record SLP1 coverage in `results.json`
Why: Experiment 01 transliterates every Devanagari language to SLP1 so that `hin_Deva` and `san_Deva` can be measured on the same footing, but SLP1 encodes the *Sanskrit* phoneme inventory and Hindi is not inside it. Two failure modes, both silent: nukta consonants (`क़ ज़ ड़ ढ़ फ़`, and the precomposed U+0958–U+095F letters) have no SLP1 phoneme and `sanscript` emits the sign as a literal ASCII `0` (`क़` → `k0a`), and signs outside the scheme — chiefly candra-o and candra-e, `ॉ ऑ ॅ` — pass through unconverted, so a string that is supposed to be ASCII still holds raw three-byte Devanagari (`डॉक्टर` → `qaॉkwara`). On FLORES-200 devtest that is 513/1012 Hindi sentences with a nukta and 256/1012 Hindi SLP1 strings still non-ASCII; `san_Deva` is hit too, at 40/1012 and 100/1012, mostly through proper nouns. Both effects inflate the SLP1 byte count and change how a tokenizer segments the string, so the `hin_Deva` SLP1 fertility and compression figures are indicative, not measurements. Rather than delete or silently keep them, `run.py` gained a pure `slp1_coverage(texts_original, texts_slp1)` that counts both failure modes per language, writes them to `results.json` under `slp1_coverage` (next to `roundtrip`), and logs them at WARNING; the experiment README labels the `hin_Deva (SLP1)` column approximate and carries the counts. No number changed: `metrics` and `parity` in `results.json` are byte-identical to the previous run.
Alternatives: dropping the `hin_Deva` SLP1 column entirely (rejected — it is a useful sanity check that Devanagari byte inflation, not Sanskrit, drives the original-script compression gap, and deleting it would hide the finding rather than qualify it); transliterating Hindi with a Hindi-aware scheme such as ISO 15919 or WX (rejected for now — it would put the two languages in different encodings, which defeats the point of the column, and CLAUDE.md §2.3 fixes SLP1 as the internal encoding; revisit if a later experiment needs Hindi text as more than a control); normalising nukta away on ingest (rejected — it silently edits the corpus every later experiment is measured on, and if ever wanted belongs in `data/` with its own entry).
Reversible: yes. `slp1_coverage` is one pure function plus one key in `results.json`; the column can be dropped, or re-derived under a different scheme, by re-running the experiment (~13 s warm).

## 2026-09-03 — Metric summaries report `mean`/`std` as `null` when there is no distribution to summarise
Why: `summarise_metric` wrote `0.0` for `mean` and `std` whenever a metric attached no per-item distribution, or attached an empty one. `0.0` is a perfectly plausible value for a fertility, a bytes-per-token or a parity ratio, so an empty or missing distribution was indistinguishable in `results.json` from a genuine measurement of zero — the failure mode CLAUDE.md §9 exists to prevent, since `results.json` is where every number lives. They are now `None` (JSON `null`), and `summarise_metric` returns a `MetricSummary` TypedDict declaring `mean: float | None` / `std: float | None` so `mypy --strict` enforces that consumers handle it. A single-item distribution still reports `std` `0.0`, which is a real measurement. No stored number changed: every metric in the current `results.json` attaches a non-empty distribution.
Alternatives: omitting the keys entirely when there is nothing to report (rejected — it makes every consumer branch on key presence, and a fixed schema is easier to diff across runs); keeping `0.0` and relying on `n` to disambiguate (rejected — `n` is the metric's own denominator, not the distribution's length, so the two can disagree).
Reversible: yes, one function and its TypedDict in `experiments/01_baseline_penalty/run.py`.

## 2026-09-03 — Tokenizer loading and metric inputs fail loudly instead of being swallowed
Why: three places treated a defect as an expected condition. (1) `registry._load_hf_arm` caught bare `Exception` per candidate, so a `TypeError` from a `transformers` signature change or a bug in `_hf_vocab_size` would be logged as "could not load", retried against three more model ids, and finally reported as "no candidate tokenizer could be loaded" — pointing every future debugging session at Hugging Face rather than at this repository. It now catches `OSError`, which is exactly the "repository not available to you" family: `huggingface_hub`'s `GatedRepoError` and `RepositoryNotFoundError` derive from `HfHubHTTPError` → `requests.HTTPError` → `OSError`, as do network failures, and `transformers` re-raises an unresolvable repo as `OSError("Can't load tokenizer for ...")`. Verified against the existing tests, which raise `OSError`, and against the live gated-repo path in the Experiment 01 re-run. Known gap, documented in the docstring: `huggingface_hub.errors.EntryNotFoundError` is *not* an `OSError` in `huggingface_hub` 1.x; `transformers` currently converts that case, and if it stops doing so the arm raises instead of falling through — the safe direction, since a mirror missing its tokenizer files is not a licence gate. (2) `tests/test_registry.py::_skip_if_tiktoken_is_offline` caught bare `Exception`, so any bug in `_load_tiktoken_arm` would turn into a green skip; narrowed to `OSError` likewise. (3) `str` is itself a `Sequence[str]`, so `fertility(tok, "rAmaH gacCati")` type-checked, ran, and returned a number computed one *character* at a time — a plausible-looking wrong answer rather than an error. `tokenizers/base.require_texts` now rejects a bare `str` with `TypeError`, and `fertility`, `compression` and `parity` (both sides) call it.
Alternatives: catching `Exception` but re-raising anything that is not a hub error (same effect, more code); leaving the metrics unguarded and relying on review (rejected — the wrong number is publishable-looking, which is the worst kind); accepting a bare `str` as a one-text corpus (rejected — it silently guesses at intent, and `[text]` is one character longer to write).
Reversible: yes, all three are single-line changes with tests pinning them.

## 2026-09-03 — Undefined per-item ratios are NaN, never 0.0
Why: compression `per_text` and parity/TPP `per_pair` can be undefined (zero tokens on one side). A 0.0 sentinel is indistinguishable from a measured zero and silently drags any mean or bootstrap CI down. NaN is visible, `numpy` handles it with nan-aware reductions, and JSON round-trips it. Every metric also records `n_undefined`.
Alternatives: 0.0 sentinel (rejected: silent contamination); dropping the item (rejected: hides that it existed).
Reversible: yes; only `metrics/` and `metrics/summary.py` change.

## 2026-09-03 — TPP is parity plus a paired bootstrap over a shared ratio core
Why: CLAUDE.md §7 defines both parity and TPP as sum(tokens_a)/sum(tokens_b) over aligned pairs; the only differences are the corpus (FLORES vs. translation corpora), the unit, and the bootstrap CI TPP requires. One core (`metrics/_ratio.py`) prevents two copies drifting. The bootstrap resamples pair indices with replacement and recomputes the ratio of sums (not the mean of per-pair ratios), 1000 draws, seed from config, 95% percentile CI.
Alternatives: independent implementations (rejected: drift); mean of per-pair ratios (rejected: dominated by short sentences).
Reversible: yes.

## 2026-09-03 — Token spans for MorphScore deferred to Experiment 04; fast tokenizers required there
Why: the `Tokenizer` Protocol only exposes `encode -> list[int]`, which is enough for every count-based metric in Experiments 01–03. MorphScore needs character spans per token. When Experiment 04 starts, add a `TokenizerWithSpans` Protocol (`spans(text) -> list[tuple[int, int]]`) satisfied by HF fast tokenizers via `return_offsets_mapping` and by trained `tokenizers` models natively; T0_gemma3 currently loads as a slow SentencePiece tokenizer and must be reloaded with `use_fast=True` (or spans reconstructed from pieces) at that point.
Alternatives: add spans now (rejected: YAGNI for Exp02).
Reversible: yes.

## 2026-09-03 — MorphScore reports F1 as `value`, precision and recall as extras
Why: `MetricResult` has one `value`. For Experiment 04, `value` = F1 of token boundaries vs. gold morpheme boundaries, with `precision` and `recall` as additional keys so over- vs. under-segmentation stays visible, per Arnett & Bergen.
Alternatives: two separate results (rejected: doubles every table).
Reversible: yes.

## 2026-09-03 — `UnigramTrainer` is not bit-for-bit deterministic; `train_bpe` is

Reversible: yes — this is an observation about upstream library behaviour, not a change to this repo's training settings; the corrected docstring can be reverted without functional effect if a future `tokenizers` release changes this behaviour (re-verify before assuming so).

## 2026-09-03 — T4 text is the model's segmentation reconciled against the raw sentence, not the raw model output

It is also recorded that the model splits compounds (samāsa) as well as sandhi, so T4 measures both; the README says so.

Reversible: yes; both variants are stored.

## 2026-09-04 — Splitter output cap is `max_new_tokens`, sized per batch, not the input's `max_length`
Why: three defects found reviewing Task 2, all in the same area — how many bytes the model is allowed to see and to emit. (1) **The output cap was the input budget.** `generate(max_length=MAX_BYTES)` capped the *total* sequence at 512 tokens, but segmentation output is systematically **longer** than its input: every restored boundary adds a separator byte and undone sandhi restores elided phonemes (example 2 of the benchmark: 17 whitespace units in, 24 out). The cap is now `max_new_tokens = min(2 × longest_input_bytes_in_batch + 32, 1024)` — sized from the batch's own longest input, so it scales with the work, generous enough never to bind on real sentences, and bounded so a degenerate repeat loop cannot run forever. On the 200 benchmarked sentences the change altered no output (200/200 identical to the pre-change run), i.e. nothing had been truncated yet at these lengths; the fix protects the long sentences of Itihāsa and the training corpus, which have not been split yet. (2) **The chunk budget ignored the prefix and EOS.** Chunks were cut to `MAX_BYTES`, then `SEGMENTATION_PREFIX` (2 bytes) and an EOS token were added, so a maximal chunk was handed to the tokeniser at 515 bytes and `truncation=True` silently dropped the last three — the sentence-final material a segmenter recovers worst. Chunks are now cut to `CHUNK_MAX_BYTES = MAX_BYTES - len(SEGMENTATION_PREFIX) - 1` and the test asserts on the *prefixed* string. (3) **The cache was flushed once per `split` call**, not per batch, so a crash in hour four of a multi-hour corpus split would have lost all four hours; `put` + `flush` now happen inside the batch loop, as soon as a sentence's last chunk returns, and a test kills the second batch and asserts the first batch is already readable from disk by a fresh `SplitCache`.
Alternatives: a fixed generous `max_new_tokens` (rejected: pads every short batch's worst case and slows the run); flushing per sentence (rejected: an fsync per sentence for no extra safety over per batch, which is the unit of loss anyway).
Reversible: yes; all three are local to `sandhi/byt5.py`.

## 2026-09-04 — Reconciliation: the threshold gates eligibility, the best window wins, and a window may not be stolen from the next unit
Why: the Task 3 addendum specifies `reconcile` as "greedily extend a window of model segments while the ratio increases and stays ≥ threshold". Read literally that is three separate rules, and the first implementation got two of them wrong in ways review caught. This entry records the reading now applied. (1) **The threshold gates eligibility, it does not stop the scan.** A compound scores 0.58 against its first segment alone and only clears 0.6 at two segments, so a scan that halted at the first sub-threshold ratio would keep every compound verbatim and silently delete the samāsa-splitting half of what T4 measures. (2) **The best window is the highest-ratio one within a bound, not the last increasing one.** Similarity is not monotone in window size — it can dip as a partly-matching segment is added and recover when the segment completing it arrives — so the scan is exhaustive over window sizes 1..`MAX_WINDOW_SEGMENTS` (8) and takes the maximum, ties to the shorter window. Eight is far above the longest real samāsa here and keeps the scan O(8) per unit while stopping a degenerate output from letting one unit swallow a sentence. (3) **A window goes to the unit with the better claim on it.** The addendum's greedy walk has no lookahead, and without one a dropped word is "repaired" by stealing its neighbour's segments: `rAmaH rAmam vadati` with `rAmaH` dropped by the model becomes `rAmam rAmam vadati` — a **case error introduced by our own pipeline**, with character retention reading a reassuring 1.000 and nothing in the manifest showing it. A window is therefore only eligible for the current unit if it resembles that unit strictly more than it resembles the next letter-bearing raw unit; otherwise the current unit is kept verbatim, which is correct, since the model did drop it. Verified on `rAmaH rAmam vadati`, `devaH devam paSyati`, `gacCati gacCatu ca` (all now preserved) and on `tataH tataH rAjA` against `tataH rAjA` (a genuine repetition, both copies kept). Because retention alone cannot show any of this, `ReconcileResult`, `CorpusSplitReport` and the split manifest now also carry `n_units_kept_verbatim` and `n_units_replaced_inexact` (replacements accepted below ratio 1.0, i.e. where the model changed characters rather than only inserting boundaries), pooled per corpus.
Alternatives: implementing the addendum literally (rejected on (1) and (2) by counter-example, on (3) because it manufactures data errors); a full dynamic-programming alignment of units to segments (rejected: more machinery than a per-unit greedy walk with one-unit lookahead, for a step whose failures are already caught by keeping unmatched units verbatim); raising the threshold instead of adding the guard (rejected: 0.80 for `rAmaH`/`rAmam` is well inside the range legitimate sandhi reversal occupies, so it would trade a duplication bug for a lost-splits bug).
Reversible: yes; `MAX_WINDOW_SEGMENTS`, the threshold and the guard are three lines each, and both output variants are stored.

## 2026-09-04 — The reconciliation window bound protects; it must never truncate
Why: re-review found that `MAX_WINDOW_SEGMENTS = 8` was a *hard* cap, and a hard cap manufactures exactly the deletion `reconcile` exists to undo. Verified on a ten-member samāsa, `devarAjaputramitrasenapativaMSakuladIpatejas` against ten model segments: similarity climbs 0.886 (8 segments) -> 0.940 (9) -> 1.000 (10), so the best window *within* the cap was eligible, was accepted, and `dIpa tejas` was dropped — a silent content loss that would have shown up as one sentence at 0.80 retention among 136,917 and been read as ordinary splitter noise. The cap is now a starting bound: `_best_window` raises it while the window at the bound is still the best-scoring one tried and segments remain (so a genuinely improving match is followed to its end), and if the best eligible window still ends exactly at the bound with segments to spare, the unit is kept **verbatim** instead of being replaced by a truncated window. Refusing to reconcile a unit is always safe — it is the module's own fallback — whereas truncating is the failure it was written to prevent. A degenerate output is still bounded in O(bound) per unit, because its ratio stops improving at once. Two behavioural tests replace the old assertion that the constant equals 8: the ten-segment compound loses no characters, and lowering the bound to 2 still splits a three-segment compound, i.e. the guarantee is the behaviour, not the number. Also in the same pass: the neighbour guard's comparison is `>=`, not `>` — an exact tie means the two raw units are the same word (`tacca tacca` against `tat ca tat ca`), and refusing both left a genuine repetition unsplit; `rAmaH` (0.80) against `rAmam` (1.00) is not a tie, so the dropped-word guard is unaffected.
Alternatives: raising the constant to 16 (rejected: it moves the cliff rather than removing it, and a compound longer than the new number fails the same silent way); no bound at all (rejected: it is the only thing stopping a degenerate output from scanning a whole sentence per unit); accepting the truncated window and counting it (rejected: a counter on a corrupted corpus is not a fix).
Reversible: yes; the scan is one function.

## 2026-09-05 — Where a sandhi-contracted boundary is placed: after the fused character, and 53% of multi-segment words are affected
Why: measured on the ingested corpus and recorded before MorphScore is computed on it, because it bounds what the primary MorphScore number can mean. The remaining 1.7% are expanded (the segments are shorter than the surface). Consequences, all of which the Experiment 04 README must state: a tokenizer scored against these boundaries is being asked to cut after the fused vowel, so MorphScore's absolute level is not comparable to a published MorphScore on a language without vowel sandhi; the bias is identical for every arm, so *paired* comparisons between arms are unaffected, which is what H3/H4 rest on; and the T5 boundary markers inherit the same placement, so the constraint forbids merges across a position that is one character off in half the multi-segment words. Fixing it properly needs a sandhi-rule-aware aligner that can mark a boundary as *inside* a character, which neither the annotation format nor the tokenizer's character-offset span model can represent.
Alternatives: place the boundary *before* the fused character (rejected: the mirror-image error, and it would split the surface so the first segment loses its final vowel entirely); drop contracted words from the gold set (rejected: 53% of the multi-segment words, i.e. most of the sandhi the project exists to study); duplicate the fused character into both segments (rejected: the offsets must index the real surface string).
Reversible: yes, one function, but re-running the ingestion and re-training the T5/T6 arms.

## 2026-09-05 — MorphScore on sandhied surfaces reports exact and ±1-character variants
Why: DCS ingestion found that 53.4% of multi-segment gold boundaries in the sandhied surface sit one character after the segment start, because vowel sandhi fuses the final and initial vowels of adjacent segments into one character (rāma + iti → rāmeti), so the boundary has no exact position in the surface. MorphScore on raw text therefore reports an exact variant (Arnett & Bergen's definition) and a variant that counts a token boundary as matching when it lies within one character of the gold offset; paired comparisons between arms use the exact variant (the offset convention is identical for both arms), and absolute MorphScore values are stated to be non-portable across studies. MorphScore on oracle-split text is exact only, since segments are whitespace-separated.
Alternatives: exact only (rejected: penalises every vowel-sandhi boundary by construction); shifting the offset by one (rejected: arbitrary).
Reversible: yes.

## 2026-09-05 — Correction: the fused sandhi character does not consistently join the left segment
Why: the entry above ("Where a sandhi-contracted boundary is placed: after the fused character, and 53% of multi-segment words are affected") states that `align_segments` "consistently places the boundary **after**" the character vowel sandhi contracted. That is **false**, and this entry corrects it; the earlier entry is left as written because this log is append-only. Verified behaviour, now pinned by regression tests in `tests/test_dcs.py` (`FUSED_SANDHI_CASES`):

| surface | segments | offsets | fused character joins |
|---|---|---|---|
| `rAmeti` | `['rAma', 'iti']` | `[4]` | left (boundary **after** the fused `e`) |
| `tatrEva` | `['tatra', 'eva']` | `[5]` | left (boundary **after** the fused `E`) |
| `vacanenEkam` | `['vacanena', 'Ekam']` | `[7]` | right (boundary **before** the fused `E`) |
| `sAgacCat` | `['sa', 'AgacCat']` | `[1]` | right (boundary **before** the fused `A`) |

The rule, which is a property of the `difflib` alignment rather than a linguistic choice: **the fused character joins the left segment, unless the sandhi output equals the right segment's first character** — `a` + `E` -> `E`, `a` + `A` -> `A`, `a` + `O` -> `O` — in which case the matcher pairs that surface character with the right segment's identical opening character and the boundary lands before it. `rAmeti` and `tatrEva` fall on the first side (`e` is not `iti`'s first character; `E` is not `eva`'s); `vacanenEkam` and `sAgacCat` on the second. A consonant sandhi that contracts nothing (`tadapi` `['tat', 'api']` -> `[3]`) is unambiguous either way. So the placement is not "one character after" the linguist's boundary in every contracted word, as the earlier entry says: it is one character after in the majority case and exact-but-on-the-other-reading in the `a` + long-vowel case, and the 53.4% contracted share the earlier entry measured is unchanged and still correct.

What does *not* change: **the convention is identical across every arm**, since all of them are scored against the same gold offsets produced by the same function, so the paired arm comparisons H3/H4 rest on are unaffected. What does: **absolute MorphScore is not portable** to a published MorphScore on a language without vowel sandhi, and the direction of the error is not even uniform within this corpus, so no constant offset correction can recover it. This is precisely why the MorphScore decisions entry above specifies a **symmetric +/-1-character tolerant variant** alongside the exact one — "within one character of the gold offset", in either direction — and not the one-sided "one character after" shift the false claim would have implied; anyone reading that entry as licensing a right-shift of the gold offsets would be wrong for half the contracted words. The T5 boundary markers inherit the same placement.
Alternatives: correcting the earlier entry in place (rejected: `docs/decisions.md` is append-only, CLAUDE.md §11); changing `align_segments` to force one side (rejected here — it is a real design question, not a documentation fix, and both sides are wrong for half the words; the tolerant MorphScore variant is the measurement-side answer); leaving the claim standing because the numbers it reports are right (rejected: Task 4's README was to be written from it, and it would have justified a one-sided offset shift).
Reversible: yes — documentation plus five regression tests; no ingested data changes, and `data/exclusion_hashes.txt` and `data/processed/dcs/` are untouched.

## 2026-09-05 — Token spans: one normalisation for three adapters, and `T0_gemma3` needed no fast reload
Why: `TokenizerWithSpans` (`src/sanskrit_tok/tokenizers/base.py`) is `Tokenizer` plus `spans(text) -> list[tuple[int, int]]`, half-open **character** offsets, in order, non-overlapping, covering every non-whitespace character exactly once; `spans_cover_text` is that contract as an executable predicate, asserted against fakes offline and against six real arms under the network gate. It is a separate protocol rather than a method on `Tokenizer` because a slow tokenizer counts tokens correctly and has no offsets at all, so Experiments 01–03 must keep working for arms MorphScore cannot score. Three consequences worth pinning. (1) **`len(spans(text))` is not a token count.** All three adapters go through one `_normalise_spans`, which clips each span to the previous one's end, trims whitespace off both edges, and drops whatever is then empty — so a token that is only the `Metaspace` marker, only the space attached to the next word, or only the tail of a character an earlier token already covered has no span. Measured: `T1_bpe_raw_64k` on `तदपि रामः गच्छति` returns 17 tokens and 14 spans. Whitespace *inside* a span survives, because multi-word tokens are real. (2) **tiktoken has no offsets API**, so `_byte_boundaries_to_char_spans` accumulates `decode_single_token_bytes` lengths into a byte cursor and maps it back through `text.encode("utf-8")`; a boundary falling inside a multi-byte character is rounded **up** to that character's end, which gives the character to the token holding its first byte and collapses the token holding only its tail. Rounding down would give one character to two tokens and break covered-exactly-once. It cannot arise on SLP1 (ASCII); it can on Devanagari, where every character is three bytes. (3) **`T0_gemma3` did not need the fast reload.** The 2026-09-03 entry "Token spans for MorphScore deferred to Experiment 04" predicted a slow SentencePiece load; measured on this environment, `T0_gemma3` resolves to `unsloth/gemma-3-4b-it` (the official `google/gemma-3-4b-it` is still gated, as recorded earlier) and `AutoTokenizer` returns `GemmaTokenizer` with `is_fast=True`, so offsets come straight from `return_offsets_mapping` and `source_id` stays `unsloth/gemma-3-4b-it`. The reload path is implemented anyway and applies to *any* slow HF arm, not just Gemma: `_FastReloadSpans` re-loads the same model id with `use_fast=True` on the first `spans` call, logs a WARNING, and suffixes `source_id` with `+fast` so `results.json` shows the substitution rather than only the log; a failed reload raises `TokenizerUnavailable` from `spans` alone, leaving every count-based metric on that arm intact. It is covered by tests only, since no arm currently triggers it. Spans sanity check on `tadapi rAmaH gacCati` and its Devanagari original: coverage holds for `T0_o200k`, `T0_gemma3`, `T0_llama4`, `T3_sarvam`, `T1_bpe_raw_64k` and `T4_bpe_split_64k`.
Alternatives: adding `spans` to `Tokenizer` itself (rejected: every existing fake and the slow-tokenizer arms would stop satisfying it); reconstructing offsets from SentencePiece pieces by string matching (rejected: ambiguous whenever a piece repeats in the word); rounding a mid-character byte boundary down (rejected: double-covers the character).
Reversible: yes.

## 2026-09-05 — MorphScore: pooled boundary F1, exclusions counted independently, one-to-one tolerant matching
Why: `metrics/morphscore.py` implements Arnett & Bergen's boundary precision/recall with `value` = F1 (docs/decisions.md, "MorphScore reports F1 as `value`…") and four choices the definition leaves open. (1) **Token boundaries exclude offset 0.** Every word starts one, no tokenizer can get it wrong, and counting it would add a free true positive to every word. Gold offset 0 is dropped for the same reason — it could only depress recall — and duplicate gold offsets are collapsed. (2) **The two exclusions are counted independently, not as a partition.** A word that is both a single token and single-morpheme increments `n_excluded_single_token` and `n_excluded_single_morpheme`, so each counter answers "how many words had this property" rather than depending on a check order that nothing in the literature fixes; their sum may exceed the number of words excluded, and the docstring says so. `n_skipped_unaligned` is a third, separate population: words whose `align_segments` returned `None` are skipped rather than scored as misses, because charging the tokenizer for the aligner's failure would make MorphScore a function of the 2.5% alignment failure rate. (3) **Tolerant matching is one-to-one and greedy nearest-first.** With `tolerance=1` each gold boundary can be claimed by at most one token boundary, so `n_matched` is simultaneously the true positives of precision and of recall and a tokenizer cannot buy recall by cutting on both sides of every boundary (`ta|d|api` against gold `[3]` scores P=0.5, R=1, not P=1). Greedy is optimal here because both sequences are sorted and the tolerance is 0 or 1, so at most two token boundaries contend for one gold boundary; a larger tolerance would need a real assignment and the docstring says that too. (4) **`value`, `precision` and `recall` are `nan` when no word was scored, including for empty input** — deliberately unlike `fertility`, which reports `0.0` for `[]`. `0.0` is a plausible measured F1 (a tokenizer that never cuts where the morphology does), so "no F1 exists" and "F1 is zero" must stay distinguishable; per-word F1 is `0.0` rather than `nan` when a scored word has no match, since a scored word always has at least one boundary on each side and `n_undefined` is therefore structurally 0. Pooling is over boundaries, not over words: on the plan's mixed example the pooled F1 is 4/7 while the mean of the per-word F1s is 5/9, and the test asserts they differ. One follow-up for Task 4: `metrics/summary.py`'s `DISTRIBUTION_KEYS` does not yet list `per_word_f1`, so `summarise_metric` reports `distribution: null` for a MorphScore result until it is added.
Alternatives: precision/recall as two `MetricResult`s (rejected earlier, doubles every table); scoring unaligned words as misses (rejected: measures the aligner); a bipartite optimal matching for the tolerant variant (deferred: identical at tolerance ≤ 1).
Reversible: yes.

## 2026-09-05 — Twelve DCS arms trained; the boundary-marker constraint halves cross-boundary tokens but cannot reach zero
Why: Experiment 04 Task 3 built the four DCS training corpora and trained all twelve `_dcs` arms, and the constraint turned out to be weaker than the earlier entry ("MorphBPE-hard implemented as boundary-marker pre-tokenisation; inference unchanged") claims. That entry says the marker means "no learned merge ever spans a gold boundary". **The learning claim is right; the inference claim it implies is not, and this entry corrects it** (the log is append-only, so the earlier entry stands as written). A BPE merge rule is a *global* character pair. The `Split(marker, behavior="removed")` pre-tokenizer stops the trainer counting any occurrence of a pair that straddles a boundary, so no rule is learned *from* such an occurrence — but a pair that is frequent in words where no boundary falls between its halves still becomes a rule, and that rule then applies inside a marked word at inference, where the text carries no markers to stop it. `morph_bpe.assert_no_cross_boundary_merges` measures exactly this residue: strip the markers from a strided 2,000-sentence sample of the marked corpus, encode, and count tokens whose span strictly contains a marker position. Measured (violations / tokens, rate), each constrained arm beside the matched unconstrained arm trained on the same sentences at the same vocabulary size:

| vocab | raw text: T1 control | raw text: T5 | oracle-split: T4 control | oracle-split: T6 |
|---|---|---|---|---|
| 32k | 8,397 / 21,307 (0.394) | **5,643 / 25,315 (0.223)** | 8,196 / 20,320 (0.403) | **4,183 / 25,707 (0.163)** |
| 64k | 8,603 / 19,207 (0.448) | **5,868 / 23,675 (0.248)** | 8,441 / 18,530 (0.456) | **4,428 / 24,419 (0.181)** |

So the constraint removes 31–48% of cross-boundary tokens and cuts the per-token rate by 43–60%, and it does *not* remove them all; on a corpus small enough that no other context supplies the crossing pair it does (the toy corpus in `tests/test_morph_bpe.py`: 0 for the constrained arm, >0 for the control, which is what pins the mechanism). Every T5/T6 `results.json` carries its own measurement and every T1/T4 BPE `results.json` carries the control, so Task 4 reads a measured contrast rather than an asserted one. **The constraint costs compression**, which Task 4's TPP analysis must lead with rather than discover: on the same 2,000 sentences T5 emits 19% (32k) / 23% (64k) more tokens than T1, and T6 26% / 32% more than T4. On one human-verified held-out sentence (`765078`, 9 words) `T1_bpe_raw_64k_dcs` gives 13 tokens and `T5_morphbpe_raw_64k_dcs` 18; `T4_bpe_split_64k_oracle_dcs` gives 11 and `T6_morphbpe_split_64k_dcs` 18. The constrained segmentation is visibly morphological (`brahmaRaspati|r`, `eta|sya`, `vIra|m` against `brahmaRaspatir`, `syAhno`, `vIram`), which is the H3 mechanism; whether it pays for itself is H4's question and is not settled here.

**The run.** Four corpora streamed from `data/processed/dcs/train.jsonl` (720,510 sentences), each exact-deduplicated on the written line, each checking **all 720,510 sentences** against the 56,242-hash exclusion list on the sandhied SLP1 form (`sentence_hash_slp1`) with **0 leaked** (CLAUDE.md §2.4): `dcs_raw` 686,044 lines, `dcs_oracle_split` 680,821, `dcs_raw_marked` 687,246 (4,093,515 markers), `dcs_split_marked` 681,346 (2,976,396 markers). The marked corpora carry 1,202 and 525 lines more than their unmarked twins (0.18% / 0.08%) because two DCS sentences with identical sandhied text can carry different annotations and so differ once marked; stripping the markers collapses each marked corpus to exactly its twin's line count (`n_out_plain`), which is the manifest field that makes the pairs matched-to-within-0.2% rather than assumed matched. All twelve arms reached their **full requested vocabulary** (no Unigram shortfall): BPE 2.5–9.7 s, Unigram 11.7–52.8 s, whole run under four minutes. Two incidental findings. (1) **The training corpora's trailing newlines are in the vocabularies.** HF `tokenizers` feeds a training *file* to the trainer with each line's `\n` attached, so the last word of every line is only ever seen as `word\n`; `T1_bpe_raw_32k` (Experiment 02) has 1,501 of 32,000 entries containing a newline. Pre-existing, identical across every arm this project has trained, and therefore harmless to paired comparisons — recorded because it is invisible until you look at a vocabulary and it does mean the effective vocabulary is slightly smaller than the nominal one. (2) `mypy` cannot check `experiments/02_tpp_parallel` and `experiments/04_morph_constrained` in one invocation now that both hold a `train_tokenizers.py` (the same pre-existing duplicate-module limitation that already applies to the three `run.py` files); the two are checked in separate invocations, both clean.

**Shared machinery.** `sanskrit_tok.tokenizers.training` now holds what the two training scripts have in common — `SideSpec`, `ensure_training_corpus`, `corpus_is_current`, `select_arms_to_train`, `train_arm`, `write_arm_results`, `build_arg_parser` — plus `build_streamed_corpus`, the new streaming builder the DCS corpora need (`ensure_training_corpus` takes its sentences in memory, and `train.jsonl` is 437 MB). The Experiment 02 script imports all of it and is otherwise unchanged; re-running it skips all twelve of its existing arms and writes nothing, and its tests (minus the six that moved to `tests/test_tokenizer_training.py` with the code) pass unchanged. `LoadedTokenizer` gains `variant` (`"dcs"` / `"oracle_dcs"` / `""`) and `list_tokenizers` a `variant=` filter, because `T4` now spans two experiments — four ByT5-split parallel-corpus arms and four gold-split DCS arms — and pooling them would be a silent error.
Alternatives: declaring the residue a bug and forbidding the crossing merge rules post hoc (rejected: removing rules from a trained table changes the vocabulary size and breaks the matched-vocabulary comparison, CLAUDE.md §2.5 — and MorphBPE itself constrains learning, not application, so this *is* the method); inserting markers at inference (impossible: the boundaries are what a tokenizer is being asked to find); deduplicating the marked corpora on their marker-stripped form to force exact line-count parity (rejected: it would silently discard one of two genuinely different gold annotations; the 0.2% gap is recorded instead); renaming the exp04 script to dodge the `mypy` duplicate-module limit (rejected: the plan names the file, and two invocations cost nothing).

## 2026-09-05 — Experiment 04 measurement choices: per-boundary violation rate, whitespace-trimmed spans, both granularities and both tolerances everywhere
Why: Task 4 needed five things the earlier Experiment 04 entries leave open or get slightly wrong, and each of them changes a number in `outputs/04_morph_constrained/results.json`. (1) **The violation audit's denominator is gold boundaries, not tokens.** `morph_bpe.assert_no_cross_boundary_merges` reports `violation_rate` = violating tokens / all tokens, which is the wrong quantity for comparing a constrained arm with an unconstrained one: the constrained arm emits *more* tokens for the same text, so a per-token rate flatters it twice — once for respecting boundaries and once for being verbose. `run.py`'s `violation_report` adds `violations_per_boundary` = violating tokens / gold boundaries in the audited text, which is the same denominator for both arms of a pair, and the README leads with it.
